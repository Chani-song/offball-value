    Source & method

    Measured
    Player and ball positions from IDSSE Bundesliga tracking at 25 Hz. Available space is the beneficiary's goal-weighted residual space under the observed defensive configuration. Space created is that quantity minus the same one with the selected defenders replaced by a no-reaction baseline. Both come from offball_value.goal_weighted_influence on the Fernández & Bornn (2018) influence surface. The browser recomputes them for whichever players you pick; they agree with the Python implementation to float64 precision.
    Current solver
    Completion proxy is the pass model the solver runs: a 33-feature logistic on kick-time positions, from Andrew's ExpectedPass (experimental_pass.json). The artifact declares validation_status: experimental_proxy and target_semantics: annotated_receipt_proxy, and the loader refuses it unless a caller explicitly opts in — the solver CLI passes --allow-proxy-labels. Its receiver labels are proxy annotations, not validated pass-completion labels, which is why it is called a proxy here and never a pass success probability.
    Positional threat is the solver's own payoff component (positional_threat_all), bounded to [0.2, 1]. Its own documentation says the scale need not be a probability.
    Release payoff is what the solver uses as the terminal value of a release: legal × completion proxy × positional threat. Legality is a gate — an offside or off-pitch target keeps its completion proxy and takes a payoff of zero. Offside uses the second-last defender of the whole defending side, and the model is shown that whole side, as the pipeline's 2v1 wrapper does.
    All four are computed by the research implementation at export time and read here; nothing is recomputed in the browser.
    Exploratory
    Explore pass model draws five targets — a 90° sector centred on the attacking direction, cut into five 25 m rays and clipped to the pitch — from whoever is within 2.5 m of the ball and at least 0.5 m closer to it than anyone else. These targets are the demo's own geometry, not the solver's action space: they were not generated, proposed or ranked by the research pipeline, and they are never labelled best or recommended. The solver's own 18 releases are built from the receiver instead (receiver + direction × offset) and belong to states this demo does not publish. Pointing our rays at the real model explores its response surface; the values are real, the targets are ours.
    Derived
    Kinematic reachable area is action_space.solve_endpoint_motion: one constant acceleration for a chosen duration, then cruise, over a 2.0 s horizon at up to 9 m/s and 3.5 m/s², tested on the 1 m action grid and required to stay inside the pitch. It is where the motion model says a player could arrive — model reachability, not an observed or estimated probability. The repository also implements a richer steering model (steering_reachable, tangential and normal control with plant-and-cut) which the defender-response pipeline uses; it costs about 9.5 s for one player at one frame, so it is not what this layer draws.
    Solver
    Solver solution is output from the exact 2v1 game in mit_ssac2027 — a separate repository and a batch job, never run in the browser. Trajectories, equilibrium value, certificate gap and root action probabilities are read from the artifact as produced, with the run's repository, commit, state index and policy fingerprint attached. No solver artifact exists for any scene in this demo, so every scene reports Not computed for this scene. Nothing is substituted in its place: a generated trajectory is not a solver result.
    Human-reviewed
    Submission showcase is a curated set of 21 dilemma scenes. The runner, defender and beneficiary shown when a case study opens are the reviewers' own labels, and the 5/5-style badge is what two reviewers each scored it out of five — human reviewer ratings, not a model output, not a probability. Five entries are solver-derived states whose tracking is not part of this published demo; they are listed with that reason rather than shown. The Full explorer collection keeps all 45 annotated scenes.
    Human
    Which players are runner, defender and beneficiary comes from manual annotation of 45 scenes (shot_annotations.xlsx, effect strong and medium). The notes are a reviewer's qualitative comment, not a metric.
    Explanatory
    The held defender is a what-if device, not a learned or optimised defensive response — this repository has none. Reacts most is an exploratory geometric heuristic on the goal-side marking target, not a research-pipeline output. Run starts come from the repository's kinematic onset detector where it fires, otherwise from a labelled acceleration cue.
    Not yet computed
    The Counterfactual and Evaluation modes are built around quantities the research code does not implement yet: the relative rank of the observed action among feasible alternatives, its similarity to the optimal action, regret against that optimum, the paired static/responsive comparison on one scale, frame-by-frame player scoring and clip-level aggregation. None of these is estimated, approximated or stood in for here. Each field states its own reason, and a field with no value cannot carry a number — the contract that produces this page refuses to construct one. When the evaluation pipeline lands, the fields populate from it with the producer's own definition version attached.
    The one regret that does exist in the repository belongs to a different lineage — it compares defender options under the legacy OBSO stack — and is deliberately not shown here as if it were this quantity.
    Legacy / reference diagnostic
    An OBSO stack — pitch control × ball transition × a static EPV grid — is implemented in this repository and still covered by its tests, but it is not part of the current solver's release payoff and is no longer shown in this interface. The version of the demo built around it is preserved on the backup/ssac-obso-demo branch.
    Not shown
    No calibrated xT, pass probability, dribble probability or learned threat surface is drawn, because this repository does not produce one.
