# demo_viz — a storytelling renderer for off-ball value scenes

`demo_viz` turns one off-ball sequence into something a first-time viewer
understands in ten seconds:

```
OFF-BALL RUNNER MOVES  ->  DEFENDER IS PULLED  ->  SPACE OPENS  ->  BENEFICIARY GAINS
```

It reads the manual annotations in `shot_annotations.xlsx`, pulls the matching
25 Hz IDSSE tracking window, and renders a broadcast-style animation with a
persistent causal-chain rail, a following camera, a runner trail, a
runner→defender tether, a shaded open-space field, a held-position
counterfactual defender, and a live chart of the space the beneficiary holds.

It is a **visualization module**. It does not change any scientific method in
this repository; it calls the ones that already exist and renders what they
return.

---

## Interactive explorer

Two front ends, one set of rules:

| | |
| --- | --- |
| **Browser** | [live demo](https://chani-song.github.io/offball-value/) · static, no server, no build step · [`web/`](web/) |
| **Local** | `python -m demo_viz.app.interactive_app` · Dash · [`app/`](app/) |

Both ask the question the videos can only answer once:

> if **this** player makes the run, which defender gets pulled, where does space
> open, and which teammate gains?

```bash
uv pip install -e ".[app]"          # or: pip install -e ".[app]"
.venv/bin/python -m demo_viz.app.interactive_app
# open http://127.0.0.1:8060
```

Options: `--port`, `--host`, `--scene <clip id>`, `--mode {manual,annotation,pipeline}`, `--debug`.

### The role dock

Beside the pitch:

```
ATTACK                              DEFENCE
  Runner  [ #10 … × ] [ #7 … × ]      Defender [ #23 … × ] [ #11 … × ]
  Beneficiary [ #9 … × ]
```

Runner and Beneficiary share the **Attack** box, because the same attacker can
hold either — but never both at once. Defender is separate. **Every role holds
as many players as the scene needs**; the annotations contain scenes with two
runners and two defenders.

Click a player on the pitch and they take a role. Four rules, in this order:

1. an **armed slot** (click the slot first) **toggles** a compatible player in
   or out of it, and stays armed for the next click;
2. otherwise a player who already holds a role **loses it** — a second click is
   always undo;
3. otherwise the clicked **side** decides: a defender fills Defender;
4. an attacker fills **Runner** when empty, else **Beneficiary**.

So the quick path is three clicks, and clicking a slot first always wins when
you want to be explicit. Clicking another compatible player **adds** them; only
`Reset` or an explicit clear empties a whole role. The × on a chip removes just
that player. Rows in the hint list do the same thing as clicking that player,
which is the fastest way to compare two defenders.

While a slot is armed the side that can fill it comes forward and the other
side drops back, so the pitch itself shows what is clickable.

The browser build additionally supports **drag and drop**: drag a player or a
chip onto a slot. Each chip is dragged on its own, so dragging one Runner chip
onto Beneficiary moves **that player only** and leaves the other runners. It
uses pointer events rather than the HTML5 drag API, which does not work on SVG.
The Dash build is click-to-arm only, on purpose — Dash has no drag primitive
and reliability matters more than the gesture.

### Scenes

The dropdown offers every annotated scene with a complete triplet at the effect
labels you tick — **Strong** and **Medium** by default, 45 scenes. Low and
ignore rows are not in the public demo.

### Modes

| Mode | Where the roles come from |
| --- | --- |
| **Manual** | nothing preselected; you click |
| **Annotation** | preloaded from `shot_annotations.xlsx`, then editable |
| **Pipeline** | a triplet file if one exists, then editable |

Pipeline mode reads the first file it finds of
`data/processed/pipeline_triplets.json`, `demo_viz/data/pipeline_triplets.json`,
`demo_viz/data/suggested_triplets.example.json`. The repository only ships the
last one, which is **not** research-pipeline output — it is generated by
`demo_viz.core.role_logic.auto_triplet` so the mode is demonstrable, and the app
labels it *from example file* on screen. Drop a real file at the first path and
it takes priority.

### Controls

`Scene` · `Mode` · `Pick` · `Auto triplet` · `Reset` · play/pause ·
`Run` / `Reaction` / `Peak` jump buttons · time scrubber ·
layer toggles (`Runner movement`, `Defender response`, `Space map`,
`Defender if stayed`, `Player numbers`, `Suggested players`, and — off by
default — `Passing lane`, `Player movements`) ·
`Full pitch` / `Focus` · `Available space` vs `Space created` ·
`PNG` · `JSON` · `Source`.

`Focus` crops to the picked players; `Full pitch` is the default and is what you
want while clicking. `Source` opens the provenance and method panel — what is
measured, what is human-supplied, what is explanatory, and what is deliberately
not drawn.

`PNG` re-renders the current pick through the *video* renderer
(`demo_viz.animate.render_still`), so an exploratory click can be exported at
presentation quality. `JSON` saves the current triplet with the run-start frame
and the method that found it.

### What the numbers mean

* **Available space** (the default) — the beneficiary's goal-weighted residual
  space, as measured. From `offball_value.goal_weighted_influence`, computed
  through a factored cache that reproduces `target_residual_influence` exactly
  (asserted in `tests/test_demo_viz_app.py`).
* **Space created** — that same quantity minus itself with the selected
  defenders replaced by a no-reaction baseline. It is a difference against a
  what-if, so it is the interpretation; Available space is the measurement, and
  that is why it leads.
* **Reacts most** — a geometric response score built on
  `offball_value.dynamic_marking`: how much of a defender's motion points at the
  moving goal-side point in front of the runner, plus how close they stay. A
  transparent heuristic, **not** a model of defensive intent.
* **Gains most** — teammates ranked by that same Space created difference. This is
  the quantity the demo is about, so the ranking is the real answer rather than a
  proxy.
* **run starts** — `offball_value.run_onset.detect_kinematic_run_onsets` where it
  fires, otherwise a labelled peak-acceleration cue. The panel says which.

### Browser build

```bash
python -m demo_viz.web.export_data        # 45 scenes -> demo_viz/web_data/
python -m demo_viz.web.build              # -> demo_viz/web_build/ + a size report
python -m http.server -d demo_viz/web_build 8090
```

Plain HTML, CSS and seven ES modules; no bundler, no runtime dependency. The
residual-space arithmetic is ported to JavaScript, so the browser recomputes
**any** triplet the visitor picks rather than replaying a pre-rendered one.
`python -m demo_viz.web.validate` runs the JavaScript in headless Chrome and
compares against Python: 160 random cases agree to float64 machine precision
(worst absolute difference 1.4e-13). `--bench` measures latency; role switching
is 0.8 ms.

The page takes URL state, so a pick is linkable:
`?scene=<clip id>&r=7&d=11&b=34&t=240&fit=1&about=1`.

```bash
    --scene J03WOH:shot_006_P1_1054 --png --mp4 --gif --html --beats

# all five 'strong' scenes, into demo_viz/exports/
.venv/bin/python -m demo_viz.export_preview --all-strong

# the demo reel — off-the-ball investigation examples: the five 'strong' scenes
# with their full human annotation (every annotated runner, defender and
# beneficiary), plus a montage, into demo_viz/exports/strong/
#
# Each video names the roles one at a time over its opening frame, settles back
# to the play framing, then runs the scene with every role and the space field
# held on from the first frame. The captions walk the causal chain on a fixed
# clock rather than on detector times, which the frame states under the
# timeline; nothing measured is paced.
.venv/bin/python -m demo_viz.export_strong

# interactive viewer in a browser
.venv/bin/python -m demo_viz.view_scene --scene strong:0

# side by side with the annotation app's own tracking plot of the same window
.venv/bin/python -m demo_viz.compare_clip --scene J03WOH:shot_006_P1_1054

# no data on this machine? this still works
.venv/bin/python -m demo_viz.render_scene --scene synthetic --png --gif
```

Scene ids accepted anywhere `--scene` is used:

| form | meaning |
| --- | --- |
| `J03WOH:shot_006_P1_1054` | a clip id from the annotation spreadsheet |
| `strong` / `strong:2` | the *n*th renderable annotated scene with that effect |
| `medium:0`, `low:3` | same, other effect labels |
| `path/to/records.json` | pipeline-predicted triplets (see below) |
| `synthetic` | generated smoke-test scene, clearly labelled as such |

## Data it needs, and how it finds it

Every input is resolved from an environment variable first, then from a short
list of conventional locations (`demo_viz/config.py`). Nothing is hard-coded to
one machine, and a missing *optional* input degrades gracefully.

| input | env var | default search |
| --- | --- | --- |
| IDSSE positions + matchinformation XML | `OFFBALL_IDSSE_DIR` | `data/raw/bundesliga-integrated/`, `~/idsse_shots/idsse-data` |
| `shot_annotations.xlsx` | `OFFBALL_ANNOTATIONS` | repo parent, repo root, `~/idsse_shots/output/` |
| shot clip videos (optional) | `OFFBALL_CLIP_DIR` | `~/idsse_shots/output/ALL_SHOT_CLIPS` |
| 5 Hz overlay cache (optional, validation only) | `OFFBALL_OVERLAY_CACHE` | `~/idsse_shots/output/tracking_overlay_cache` |
| scene cache (written) | `OFFBALL_DEMO_CACHE` | `demo_viz/cache/` |
| exports (written) | `OFFBALL_DEMO_EXPORTS` | `demo_viz/exports/` |

`demo_viz/cache/` holds two kinds of derived file, both safe to delete:
`clocks/*.json` (first frame of each half per match) and `windows/*.npz`
(one extracted tracking window each, with a `.json` sidecar naming its source).

## Architecture

Six layers, each usable on its own.

```
config.py           where the data is
  |
sources/            1. discovery + loading
  idsse.py            fast line-streaming window reader over the positions XML
  annotation_scene.py joins a spreadsheet row to a tracking window
  pipeline.py         the same for pipeline-predicted triplets
  synthetic.py        generated scene for smoke tests
annotations.py        shot_annotations.xlsx -> AnnotatedClip records
  |
scene.py            2. canonical Scene object   <-- everything downstream uses only this
  |
quantities.py       3. optional quantities, each from a named repo function
  |
render/             4. rendering primitives
  pitch.py            pitch geometry
  layers.py           trail, tether, wake, ghost, lane, run vector, gain badge
  camera.py           smooth following viewport
  labels.py           collision-aware label placement
  figure.py           full-frame composition
story.py            5. storytelling layer: beats, captions, layer strengths
animate.py          6. export: still / MP4 / GIF / contact sheet
interactive.py        optional: self-contained Plotly HTML
loader.py             one entry point tying the above together

render_scene.py     CLI: one scene -> artifacts
view_scene.py       CLI: interactive viewer
export_preview.py   CLI: batch export + manifest.json
compare_clip.py     CLI: before/after against the annotation app's own clip
scenes.json         presentation-only per-scene overrides
```

### The canonical `Scene`

`scene.Scene` is deliberately format-agnostic, so a change to the pipeline's
intermediate files cannot break the renderer. It carries:

* `fps`, `times` (seconds, 0 at the annotated shot), `frame_ids`
* `players`: id → `ScenePlayer` with `team_id`, `side`, `shirt`, `name`,
  `xy` `(T, 2)` in metres, optional `speed`, `is_goalkeeper`
* `ball_xy` `(T, 2)`, NaN where unknown
* `runner_ids`, `defender_ids`, `beneficiary_ids`, `carrier_ids`
* `attacking_team_id` / `defending_team_id` / `attacking_direction`
* `moments` (story beat times), `scores`, `series` (time series), `surfaces`
* optional hooks that are **`None` unless the repository really computes them**:
  `pass_probability`, `dribble_probability`, `threat_surface`
* `video_path`, `notes`, `provenance`

Coordinates follow `offball_value.bundesliga`: metres, origin at the centre
spot, `x ∈ [-52.5, 52.5]`, `y ∈ [-34, 34]`. `Scene.view_xy()` mirrors the pitch
so the attacking team always plays left-to-right on screen; all science stays in
raw coordinates and only the renderer flips.

## What is grounded, and what is only a drawing

This is the part to read before showing the demo to anyone.

### Measured — straight from data or from this repository's own code

| on screen | where it comes from |
| --- | --- |
| player and ball positions, speeds, trails | IDSSE 25 Hz tracking, unmodified |
| who is runner / defender / beneficiary | the human annotations in `shot_annotations.xlsx` |
| `RUNNER MOVES` beat time | `offball_value.run_onset.detect_kinematic_run_onsets` |
| `DEFENDER IS PULLED` beat time | the same detector applied to the annotated defender, when it fires |
| the shaded open-space field | `offball_value.goal_weighted_influence.target_residual_influence` (repo v0.1), built on the Fernández & Bornn (2018) influence surface in `offball_value.fernandez_influence` |
| the `observed` curve, the `defender held` curve, and the `+x.x` hero number | the same function, integrated over the pitch |
| "pulled N m", "ran N m", "open lane N m" | measured displacements in metres |

### Explanatory — labelled in frame, every time

| on screen | what it actually is |
| --- | --- |
| the dashed ghost defender and the `defender held` curve | the **same** repository formula re-evaluated with the reacting defender not responding — by default pinned at their pre-run position (`--baseline hold`), optionally continuing their pre-run velocity (`--baseline drift`). Either way it is a what-if device, **not** a learned or optimised defensive best response. The repository does not yet have one, and which baseline you pick changes the answer — see `OVERNIGHT_REPORT.md` §8. |
| the `DEFENDER IS PULLED` beat time *when the kinematic detector does not fire* | a geometric pursuit rule written for this demo: the defender moving faster than 1.5 m/s toward the moving goal-side point in front of the runner for 0.4 s. The goal-side point itself is `offball_value.dynamic_marking.moving_goal_side_target`; the timing rule is presentation logic and the beat table says so. |
| the `RUNNER MOVES` beat time when no onset is detected in the window | the runner's strongest sustained acceleration in the first 65 % of the window, labelled "peak-acceleration cue". |
| `--wake geometric` | a swept corridor between the defender's held and current position. Pure geometry, no metric. Only used when no surface is available. |
| `[moved +x.xxs for pacing]` in the beat table | a detected time that had to be nudged so the beats stay ordered and the last beat has screen time. The nudge is always reported. |

### Not shown at all

Calibrated xT, pass probability, dribble probability and any learned threat
surface are **not rendered**, because this repository does not currently
produce them. `Scene` has typed hooks for all four; they stay `None`, and
`tests/test_demo_viz.py` asserts that they do.

## Visual language

| role | colour | redundant encodings |
| --- | --- | --- |
| off-ball runner | magenta `#FF2D87` | larger radius, glow, direct label, trail, run vector |
| pulled defender | amber `#FFA62B` | larger radius, glow, direct label, tether, ghost |
| beneficiary | cyan `#5CE8F5` | larger radius, glow, direct label, reveal ring, gain badge |
| attacking team | warm neutral `#D9CFB8` | small radius, low opacity, team key in the panel |
| defending team | slate `#5F7392` | same |

Green is never used for a highlight — the pitch is green. Identity is never
colour-alone: every role carries at least a size change, a label and a
behavioural cue.

`python -m demo_viz.palette` prints the separation of every mark pair in normal,
protan, deutan and tritan vision (OKLab ΔE ×100). The three story roles clear
ΔE ≥ 17 against one another in *every* vision mode; the pairs it flags are
always a role against a *neutral* mark, which the renderer separates by radius,
opacity and direct label as well. `tests/test_demo_viz.py::PaletteTests` keeps
this true.

## Story mode

`story.build_storyboard(scene)` produces five beats — `play`, `runner`,
`defender`, `space`, `beneficiary` — each with a caption and a set of layer
strengths in `[0, 1]`. `Storyboard.state(t)` eases between them so the animation
glides rather than cuts, and `Storyboard.chain_progress(t)` drives the
four-chip causal rail across the top of the frame.

Beat times come from the detectors above. `story.beat_table(storyboard, scene)`
prints, for each beat, the time and exactly which detector or rule produced it.
Every CLI prints that table before rendering.

## Presentation overrides: `scenes.json`

`demo_viz/scenes.json` holds **presentation-only** settings per scene: window
trim (`before_s` / `after_s`), a one-line `headline` for the subtitle, camera
tweaks, and which space layer to shade. Nothing in that file changes a measured
quantity — it is the equivalent of a video editor's trim. Unlisted scenes fall
back to the defaults (8 s before the annotated shot, 3 s after, matching the
window the human annotator reviewed in the clip app).

## Using pipeline-predicted roles instead of the spreadsheet

`sources/pipeline.py` accepts a JSON file holding one record or a list:

```json
[
  {
    "clip_id": "J03WOH:shot_006_P1_1054",
    "runner": ["7"],
    "defender": ["11"],
    "beneficiary": ["34"]
  },
  {
    "match_id": "J03WOY", "period": 2, "period_seconds": 903.47,
    "team": "F.C. Hansa Rostock",
    "runner": ["DFL-OBJ-002FZB"], "defender": ["25", "15"], "beneficiary": ["34"]
  }
]
```

Role entries may be shirt numbers or DFL person ids; both resolve against the
match roster. A record that names neither a known clip nor
`match_id + period + period_seconds` raises with a message listing the keys it
needed, rather than quietly rendering the wrong players. Then:

```bash
.venv/bin/python -m demo_viz.render_scene --scene my_predictions.json --mp4
```

Switching between manual and predicted roles is a change of `--scene`; nothing
else in the renderer changes.

## Exported artifacts

`demo_viz/export_preview.py` writes, per scene (the hero scene is named
`preview*`, the rest by clip id):

| file | what it is |
| --- | --- |
| `*.mp4` | 1920×1080, 25 fps, with a short hold at each end |
| `*.gif` | the same clip transcoded through ffmpeg's `palettegen`/`paletteuse`, 820 px wide at 10 fps — much smaller and truer to the soft space field than a frame-by-frame GIF writer |
| `*_frame.png` | a single still at the payoff beat |
| `*_beat_N_*.png` | one still per story beat |
| `*.html` | the interactive viewer (~1.5 MB, plotly.js from CDN) |
| `manifest.json` | roles, beat times, the detector behind each beat, scores, window frames and the source clip for every scene exported |

`compare_clip.py` additionally writes `*_before_after.mp4` and the
`*_nohold.mp4` it is built from.

## Dependencies

Everything used here is already in `pyproject.toml`: `numpy`, `pandas`,
`scipy`, `matplotlib`, `openpyxl` (via pandas' Excel reader). The interactive
viewer uses `plotly`, declared as the optional `demo` extra
(`pip install -e ".[demo]"`); nothing else in the renderer imports it.
`ffmpeg` on `PATH` is used for MP4 export and for the GIF palette pass; without
it the CLIs print a warning, fall back to a frame-by-frame GIF writer, and
still produce PNG and HTML.

`scipy` is used for one thing: upsampling the coarse pitch grid before
contouring, so the counterfactual difference outline reads as a curve rather
than a polygon. The renderer falls back to the raw grid if it is unavailable.

## Tests

```bash
.venv/bin/python -m unittest tests.test_demo_viz -v
```

26 tests. Most run on the synthetic scene and need no data at all; the four
that need IDSSE tracking skip themselves with a message naming the missing
input. They cover shirt parsing, scene invariants, the view transform, that the
unavailable quantity hooks stay `None`, beat ordering and screen time, camera
aspect and smoothness, palette separation under simulated colour-vision
deficiency, rendering every beat, rendering with *no* optional quantity at all,
and the pipeline adapter's error messages.
